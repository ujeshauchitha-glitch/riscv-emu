# Phase 1 — Complete RV64I

Phase 0 built the machinery. This phase fills in the base integer instruction
set: every RV64I instruction is now implemented and tested. The emulator can run
real compiled code — the self-test in `examples/rv64i_selftest.S` is assembled by
the actual GNU assembler and executes correctly.

Still missing before an OS can boot: CSRs and trap handling (phase 2), the M and
A extensions (phase 3), and devices (phase 4).

## The `*W` instructions, and the bug they invite

RV64 keeps a full set of 32-bit operations alongside the 64-bit ones, because C
code is full of `int` arithmetic and it would be wasteful to synthesise each
32-bit add from a 64-bit add plus fixups.

The rule is: **compute on 32 bits, then sign-extend the result to 64.** Not zero-
extend. Sign-extend.

```cpp
inline u64 sext32(u32 value) {
    return static_cast<u64>(static_cast<i64>(static_cast<i32>(value)));
}
```

So `addw` producing `0x8000_0000` must leave `0xFFFF_FFFF_8000_0000` in the
register, not `0x0000_0000_8000_0000`.

This is worth dwelling on because of *how* it fails. A zero-extending
implementation passes every small-number test you write. Nothing goes wrong
until a kernel does arithmetic on a value that happens to have bit 31 set — and
then a pointer is suddenly 4 GiB away from where it should be, thousands of
instructions after the actual mistake. It is one of the most common RV64
emulator bugs and one of the most annoying to track down.

The same applies in reverse: the `*W` instructions ignore bits 32–63 of their
*inputs*. `addw` on `0xFFFF_FFFF_0000_0005` and `3` gives `8`.

## Shift amounts: 6 bits or 5

| | shift amount | selector |
|---|---|---|
| `SLLI`/`SRLI`/`SRAI` (64-bit) | 6 bits | `funct6` (bits 31:26) |
| `SLLIW`/`SRLIW`/`SRAIW` (32-bit) | 5 bits | `funct7` (bits 31:25) |
| `SLL`/`SRL`/`SRA` (64-bit, register) | `rs2 & 0x3f` | `funct7` |
| `SLLW`/`SRLW`/`SRAW` (32-bit, register) | `rs2 & 0x1f` | `funct7` |

The 64-bit immediate shifts need six bits to express a shift by up to 63, and
they take that bit from `funct7`, leaving `funct6`. The 32-bit forms cannot shift
by more than 31, so five bits suffice and `funct7` stays intact.

Masking the register forms is not optional. The spec says only the low bits are
used, but in C++ shifting a 64-bit value by 64 or more is *undefined behaviour* —
so an unmasked `a << shamt` is a real bug even on inputs where the spec would
have forgiven you.

## JALR clears bit 0

```cpp
const u64 target = (read_reg(inst.rs1) + static_cast<u64>(inst.imm)) & ~1ull;
```

Two things to notice.

First, the clear happens *after* the addition, so `jalr rd, rs1, 1` is a
perfectly legal way to reach an even address. Clearing before adding would be
wrong.

Second, this is not an alignment check — it is defined behaviour. It exists so
that bit 0 of a function pointer can carry a tag (the C extension uses this)
without confusing indirect jumps.

Also note the ordering in `execute_jalr`: the target is computed before `rd` is
written, because `rd` and `rs1` may be the same register. `jalr ra, ra, 0` is a
real idiom and would break under the obvious implementation.

## Where a misaligned-jump trap is reported

Without the C extension, instructions must be 4-byte aligned. When a jump or
branch computes a misaligned target, the spec reports the trap **on the jump**,
not on the target — `mepc` points at the instruction that did the jumping.

That is why the check lives in `Cpu::set_branch_target()`, called before
`next_pc_` is committed, rather than in `fetch()`. Checking at fetch time would
leave the PC on the target address, which tells you where you ended up but not
what sent you there — and the latter is the thing you need to look at.

The fetch-time check is still there as a backstop for a PC set some other way.

## Signed and unsigned are different instructions

Three places where the same bits are compared differently:

- `SLT` vs `SLTU`, `BLT` vs `BLTU`, `BGE` vs `BGEU`. On `0xFFFF_FFFF_FFFF_FFFF`
  and `1`, the signed forms see `-1 < 1` and the unsigned forms see the largest
  possible value `> 1`. Both are correct; they are answering different questions.
- `LW` vs `LWU` (and `LB`/`LBU`, `LH`/`LHU`). Both read the same bytes; one
  sign-extends the result to 64 bits and the other zero-extends. On RV32 there is
  no `LWU`, because there is nothing to extend into.
- Stores have no signed/unsigned variants at all — they write the low bytes of
  the register and discard the rest.

## FENCE is a no-op, and that is correct

`FENCE` orders memory operations as observed by other harts and by devices.
We are a single-hart emulator that executes strictly in order and completes each
access before starting the next instruction, so the ordering `FENCE` requests
already holds unconditionally. Implementing it as a no-op is not a shortcut; it
is a correct implementation for this machine model.

`FENCE.I` (from Zifencei) synchronises the instruction stream after
self-modifying code. We have no instruction cache and no decoded-instruction
cache, so the same reasoning applies. If a JIT or a decode cache is ever added,
this is where it would need to invalidate.

## ECALL and EBREAK "fail" on purpose

Both raise a trap, and that is how they do their job. `ECALL` is how every system
call in every RISC-V OS is made: the guest puts arguments in registers, executes
`ECALL`, and a handler takes over.

Right now a trap simply stops the emulator, because there is nowhere for it to
go. Phase 2 adds `mtvec` and the machinery to dispatch traps to a handler, at
which point `ECALL` starts behaving like a system call rather than a halt.

## Not-yet-implemented instructions trap

Three encodings share opcodes with instructions implemented here and must not be
mistaken for them:

- `funct7 == 0x01` on `OP`/`OP-32` is the M extension (`MUL`, `DIV`, ...) — phase 3
- `funct3 != 0` on `SYSTEM` is the CSR instructions — phase 2
- `SYSTEM` with `funct3 == 0` but an immediate other than 0 or 1 is `MRET`,
  `SRET`, `WFI` — phases 2 and 6

All of them raise `IllegalInstruction` with the offending bits in `tval`. A
`mul` silently executing as an `add` would be a genuinely nasty bug.

## Misaligned data accesses

The spec lets an implementation either support misaligned loads and stores in
hardware or raise a misaligned-address exception. We support them, matching
QEMU's `virt` machine — which is what the kernels we intend to boot are developed
against.

## Testing

Three layers, deliberately independent of each other.

**Unit tests** (`tests/test_rv64i.cpp`, 95 checks). Programs are built with
encoders in `tests/machine.hpp` that are written separately from
`src/decoder.cpp`. A test that used the emulator's own decoder to construct its
inputs would agree with itself no matter how wrong both halves were; two
independent implementations agreeing is actual evidence.

**A real-toolchain self-test** (`examples/rv64i_selftest.S`). Assembled by GNU
`as` and linked at `0x8000_0000`, so the emulator is decoding bytes produced by
an independent, battle-tested assembler. It runs 14 checks over the corners
above and accumulates one bit per check into `a0`; `a0 == 0x3fff` means all
passed, and a clear bit names the one that did not. Wired into CTest, and skipped
automatically when no RISC-V toolchain is installed.

This layer earned its keep immediately: it caught a mistake in the test itself
(an `auipc` label placed after the instruction rather than on it) where the
emulator was right and the test was wrong.

**Regression tests** from phase 0 (`test_decoder`, `test_bus`, `test_cpu`) still
run unchanged.

```bash
cmake -S . -B build && cmake --build build
cd build && ctest --output-on-failure
```

To get the self-test running:

```bash
apt-get install gcc-riscv64-unknown-elf
```
